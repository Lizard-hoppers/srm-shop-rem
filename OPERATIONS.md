# OPERATIONS — Electronics CRM

Сверяться с этим файлом в начале и в конце каждой рабочей сессии (правило
Clean & Live Bot Manifest, п.10).

## Что это

CRM для магазина электроники + мастерской по ремонту: клиенты, склад по
ячейкам, ремонты с привязкой к мастеру, приход комплектующих от
поставщиков, продажи (онлайн/офлайн). Весь интерфейс персонала — единое
Telegram Mini App (не отдельная веб-панель + отдельный бот, как было в
исходном плане — решение поменялось по ходу разработки). Общая
SQLite-база (WAL).

**Вход:** только по Telegram ID, без пароля (кроме самого первого раза для
нового сотрудника — см. «Онбординг нового сотрудника» ниже). Сессия не на
cookie (Telegram-вебвью ненадёжно их сохраняет между запросами), а на
подписанном токене `?t=...`, который прокидывается через каждую
ссылку/форму/редирект (`webapp/deps.link()` и `webapp/templating.render()`).

**Роли (RBAC):** `owner`/`admin`/`master`/`storekeeper` в колонке
`staff.role`, проверяются через `webapp/deps.require_role(*roles)` (поверх
`require_staff`). `/reports` — только owner+admin; мутации склада
(`/inventory/products`, `/cells`, `/movements/*`) — owner+admin+storekeeper;
мутации ремонтов (создание/статус/назначение/цена/детали) —
owner+admin+master. Просмотр списков (GET) открыт всем залогиненным. До
18.08 ролей не было вообще — любой залогиненный видел выручку и мог
списывать склад, см. commit `2c0d491`.

## Уведомления в рабочую группу

Рабочая группа — Telegram-форум «Работа» (`chat_id=-1004478202416`, бот в
ней админ с `can_manage_topics`), с отдельными темами под разные потоки
заказов:

| Тема | thread_id | Статус |
|---|---|---|
| Ремонт техники | 5 | подключена — карточка на каждый новый ремонт |
| Заказы офлайн (клиент заказывает то, чего нет на складе, под заказ у поставщика) | 3 | информационная, ничего не постит пока — нет отдельной сущности "заказ под клиента" в схеме |
| Онлайн заказы: Olx, Prom | 12 | информационная — задел под будущую интеграцию с OLX/Prom.ua (синхронизация остатков) |

Отдельно есть плоская группа «Мастера 007» (`chat_id=-1003820178638`, без
тем, бот там тоже админ) — общий чат всех мастеров по ремонту (пока один на
всех, без разделения по мастерам).

При приёме устройства в ремонт (`POST /repairs`) `crm_web` шлёт карточку
(клиент, телефон, устройство, неисправность, мастер, оценка, канал)
напрямую в Telegram Bot API (`core/notify.py`, `httpx` →
`api.telegram.org`, без похода через процесс `crm_bot`) в **оба места
сразу**: тему «Ремонт техники» и группу «Мастера 007»
(`notify_repair_card()` → `CRM_STAFF_GROUP_CHAT_ID`+`CRM_REPAIR_TOPIC_ID=5`
и `CRM_MASTERS_GROUP_CHAT_ID`). Каждое из трёх назначений (`_send()` в
`core/notify.py`) независимо: если конкретная переменная не задана — тот
конкретный пункт молча пропускается, остальные всё равно уходят; ошибка
Telegram API тоже только логируется, запрос не падает.

**Кнопки на карточке (18.08).** Карточка не статичная — под ней кнопки,
которые ведут ремонт по статус-пайплайну прямо из Telegram, без захода в
приложение:
- `new` → «🔧 Взять в работу» (`repair_take:{id}`) — атомарно
  (`core/repairs.claim_repair()`, `UPDATE ... WHERE status='new'` +
  проверка `rowcount`, а не слепой `UPDATE` — вторая одновременная попытка
  просто проигрывает гонку, а не тихо перезаписывает первую). Если на
  приёме уже назначили конкретного мастера — кнопка реально сработает
  только для него (или admin/owner), остальные получат алерт «Закреплено
  за …».
- `in_progress` → «✅ Готово» (`repair_done`, только для взявшего мастера
  или admin/owner с `override=True`) и «↩️ Отменить» (`repair_release`,
  возврат в `new` без мастера — на случай, если взяли по ошибке).
- `ready`/`issued`/`cancelled` → кнопок нет.

Карточка **редактируется на месте** (`core/notify.edit_message()` /
`sync_repair_cards()`), а не дублируется новым сообщением — какое именно
сообщение редактировать, знает новая таблица `repair_order_messages`
(`chat_id`+`message_id` на каждый отправленный адресат). Синхронизация
двусторонняя: ручная смена статуса из приложения (`POST
/repairs/{id}/status`) тоже дёргает `sync_repair_cards()` — кнопка в
Telegram и статус в приложении никогда не расходятся, старая карточка не
может позволить нажать «Готово» на том, что уже закрыли из приложения.

Обработчики кнопок — `bot/repair_actions.py` (три `callback_query`
хендлера, зарегистрированы в `bot/bot.py`), сотрудник определяется по
`callback.from_user.id` через `core.auth.get_staff_by_telegram_id()` —
тот же путь, что и вход в веб-панель.

**Как узнать chat_id/thread_id новой темы:** добавить бота в группу как
админа → открыть тему → скопировать номер из ссылки `t.me/c/<internal_id>/<thread_id>`
(chat_id = `-100<internal_id>`), либо отправить `/chatid` в общем чате
группы (не в теме) — бот ответит числом chat_id самой группы. thread_id
темы командой не достать, только из ссылки на сообщение в этой теме.

**Дальше по плану (не реализовано):** разбить общую группу «Мастера 007»
на подгруппу под каждого выбранного мастера — обсудить структуру, когда
владелец определится с реальным составом мастеров (сейчас в `staff` только
3 заглушки: Мастер 1/2/3).

## Карточка товара (18.08, commit `aa6af0a`)

Строки в «Склад → Товары» кликабельны → `/inventory/products/{id}` —
просмотр (все роли), форма редактирования и загрузка фото (owner/admin/
storekeeper, `_STOCK_WRITE_ROLES`, как и другие складские мутации в
`webapp/routers/inventory.py`). Фото — файл на диске
`webapp/static/product_photos/{product_id}_{uuid4}.{ext}` (свой filename
генерируется всегда, никогда не берётся у клиента — от path traversal),
content-type валидируется по allowlist (jpeg/png/webp) на сервере, старое
фото удаляется при замене. Директория в `.gitignore` (runtime-данные, не
исходники) — на новом сервере создаётся автоматически при первой загрузке
(`os.makedirs(..., exist_ok=True)`). `products.photo_path` — новая
колонка через `_ensure_column()` (таблица уже с боевыми данными на
проде, не свежий `CREATE TABLE`). 146/146 тестов. Проверено вживую:
реальная карточка (id=7) открылась, тестовый товар отредактирован и
фото реально легло на диск + отдалось по `/static/product_photos/...`.

**Баг и фикс 18.08 (commit `7d7fdba`): загрузка фото товара «вешала»
мини-приложение.** Причина — в `/etc/nginx/sites-available/crm-miniapp`
не было `client_max_body_size`, действовал дефолт nginx 1 МБ; реальное
фото с камеры — обычно 2-8 МБ. Форма загрузки была обычным `<form
enctype="multipart/form-data">` (нативная навигация браузера, не AJAX) —
когда nginx резал запрос, странице некуда было вывести ошибку, и
Telegram WebView просто зависал на пустом экране в процессе навигации
(сам Telegram не падал). **Важно помнить:** у этого домена nginx
настроен без `client_max_body_size` по умолчанию — если добавляется
новый эндпоинт с загрузкой файлов, лимит уже поднят до 20M на весь
`location /` (общий для всего сайта), но если появится домен/сайт с
нуля — не забыть про этот же нюанс.
Фикс: `client_max_body_size 20M;` в nginx (бэкап старого конфига рядом,
`nginx -t` + reload) + оба фото-эндпоинта (`/inventory/products/{id}/photo`,
`/purchases/scan`) теперь режут чтение на 15 МБ сами и отдают
дружелюбный JSON 413 вместо чтения без лимита; форма загрузки фото товара
переведена на `fetch`+`FormData` с индикатором «Загружаю…» и текстом
ошибки вместо голой навигации. 149/149 тестов. Проверено вживую через
реальный HTTPS-домен (не localhost) синтетическим ~4 МБ фото — раньше
упёрлось бы в старый лимит 1 МБ, теперь 200 OK меньше чем за секунду;
25 МБ файл (выше нового потолка) отклоняется чисто 413, сервис не падает.

**Карточки товаров вместо таблицы (18.08, commit `642f53d`).** «Склад →
Товары» — сетка карточек `.cards`/`.card` (тот же паттерн, что на
дашборде/хабах), 2 колонки, маленькое квадратное фото сверху (или
плейсхолдер-иконка), название, SKU+категория, «Остаток: N шт (мин. M)».
Заодно разобрался с жалобой «показывает 05 вместо 5»: это была не одна
проблема, а две — (1) у товара #7 поле «Единица» реально содержало текст
`"5"` вместо `"шт"` (опечатка при вводе, не баг кода), старая таблица
склеивала `{{ qty }} {{ unit }}` без подписи → «0 5» читалось как «05»,
поправлено в БД напрямую; (2) поле «Мин. остаток» на форме создания имело
`value="0"` (не placeholder) — на мобильном при тапе в поле с уже
непустым «0» и допечатывании цифры легко получить «05» (для Python
парсинга не страшно, `int("05")==5`, но именно так, похоже, разъехались
поля при вводе) — заменено на `placeholder="0"`, дефолт 0 при пустом
поле остаётся через `optional_int(...) or 0` на сервере. 154/154 тестов
(чистый UI/CSS, тесты не менялись).

**Чекбоксы товара — правились дважды (18.08, commit `53dcf30`,

может не обновиться по тому же URL, пока процесс не перезапущен.

**«Единица» — выпадающий список, не текст (18.08, commit `5586b79`).**
Баг «5 попадает в поле Единица» (см. выше, товар #7) повторился ЕЩЁ РАЗ
после первого ручного фикса данных — оказалось, это не разовая опечатка,
а системная уязвимость: текстовое поле рядом с числовым легко словить
случайный ввод на мобильном. Убран `<input type="text">`, теперь
`<select>` (шт/уп./компл./м/пара, «шт» по умолчанию) — вписать туда
цифру физически нельзя. На форме редактирования: если у товара уже
сохранено значение единицы не из этого списка (легаси-данные), оно
добавляется отдельным `selected`-option с точным текущим значением —
сохранение других полей карточки никогда не должно тихо подменять
единицу на «шт» как побочный эффект.

**«Единица» — снова переделано, теперь без `<select>` (18.08, commit
`d76294f`).** Даже выпадающий список не спас — Павел сообщил, что после
выбора значения выскакивало ВТОРОЕ «прозрачное телеграмовское меню» с
повторным выбором. Похоже, Telegram WebView сам перехватывает нативный
`<select>` под свой picker независимо от нашего HTML/CSS (та же природа
проблемы, что описана в шапке `select-enhance.js` про другие вебвью —
просто здесь бьёт иначе). Убрал `<select>` вообще, поставил тот же
`<input list="unitList">` + `<datalist>`, что уже проверенно работает в
поиске товара на «Приходе» и в каталоге устройств при приёме ремонта —
обычное текстовое поле с подсказками, а не модальный picker, так что
телеграму нечего перехватывать. Ячейка на новой форме «Добавить остаток»
(ниже) осталась настоящим `<select>` — на неё жалоб не было, менять её
заодно не было причины.

**Добавить остаток прямо с карточки товара (18.08, commit `d76294f`).**
Второй репорт Павла — «некуда вписать сколько товара осталось». По
архитектуре остаток считается по ячейкам через леджер
`core.inventory.record_movement()` (manifest п.11 — в обход леджера
списывать/приходовать нельзя), поэтому прямого числового поля на самом
товаре никогда не будет. Вместо этого — мини-форма «Добавить остаток» на
карточке товара (`POST /inventory/products/{id}/receive`, ячейка+кол-во,
дергает тот же `receive_stock()`, что и полноценный «Приход»). Заодно
создание нового товара теперь сразу редиректит на его карточку (было — в
общий список), чтобы сразу было куда добавить остаток, не разыскивая
свежесозданный товар в списке. 158/158 тестов, проверено вживую полным
циклом (создал → попал на карточку → добавил остаток → леджер реально
сдвинулся).

## Онбординг нового сотрудника

Входа по паролю нет вообще, поэтому нового сотрудника подключает владелец
вручную:
1. `python -m core.bootstrap <login> <password> <имя>` — создать аккаунт
   (роль передаётся внутри команды, см. файл).
2. Попросить сотрудника прислать свой Telegram ID (например, через
   `@userinfobot`).
3. `python -m core.link_telegram <login> <telegram_id>` — привязать.
4. Дальше сотрудник просто открывает бота — входит по ID, без пароля.

## Локальный запуск (разработка)

```
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env   # CRM_SECRET_KEY, CRM_BOT_TOKEN, CRM_MINIAPP_URL, CRM_STAFF_GROUP_CHAT_ID (опционально)
export $(cat .env | xargs)
python -m core.bootstrap owner <пароль> "Имя владельца"
python -m core.link_telegram owner <telegram_id>
uvicorn webapp.main:app --reload --port 8099   # веб-часть mini app
python -m bot.bot                               # бот (меню открывает mini app)
```

## Тесты

`python simulate_tests.py` — сценарные тесты ядра (клиент→устройство→ремонт,
полный пайплайн ремонта, приход, продажи со списанием и нехваткой остатка,
telegram initData, url-токен). Работают на временной SQLite-базе во
временной директории, живую базу не трогают. Обязательны перед каждым
деплоем.

**Важно:** при ручном smoke-тесте через curl на живом сервере всегда
задавать `CRM_DB_PATH` на временный файл, либо вручную чистить тестовые
записи из `crm.sqlite3` после — один раз уже забыли и замусорили прод-базу
тестовым клиентом/товаром/ремонтом, пришлось чистить вручную.

## Деплой (Server-First, манифест п.8)

Продовая директория на BlueVPS: `/opt/electronics_crm`. Реальный процесс
пока проще, чем классический candidate/live манифеста (проект молодой,
один разработчик): rsync прямо в `/opt/electronics_crm` (с исключениями
`.venv`, `.git`, `.env`, `crm.sqlite3*`) → `simulate_tests.py` в venv на
сервере → `systemctl restart crm_web` (`crm_bot` перезапускать только если
менялся код бота) → проверка `journalctl -u crm_web -f`. Когда сотрудников
станет больше — вернуться к полноценному candidate-шагу.

systemd-юниты: `crm_web.service` (uvicorn на 127.0.0.1:8099), `crm_bot.service`
(polling). nginx + certbot на `crm.2.59.217.221.sslip.io` проксирует на
:8099 (паттерн как у `taki-verify`).

## Нельзя (манифест п.11 + специфика проекта)

- Ручной `ALTER TABLE` — только через `_ensure_column()` в `core/storage.py`.
- Хранить `CRM_SECRET_KEY` / `CRM_BOT_TOKEN` в репозитории — только в `.env`
  на сервере (в `.gitignore`).
- Списывать/перемещать товар в обход `core/inventory.record_movement()` —
  это единственный путь, который держит `stock` и `stock_movements` в
  согласованном состоянии.
- Полагаться на cookie/сессию для аутентификации в вебе — Telegram-вебвью
  их не держит между запросами, поэтому вся навигация обязана прокидывать
  `?t=` токен через `link()`/`render()`, иначе пользователя выкинет на
  повторный вход.
