# OPERATIONS — Electronics CRM

Сверяться с этим файлом в начале и в конце каждой рабочей сессии (правило
Clean & Live Bot Manifest, п.10).

## Что это

CRM для магазина электроники + мастерской по ремонту: клиенты, склад по
ячейкам, ремонты с привязкой к мастеру, приход комплектующих от
поставщиков, продажи (онлайн/офлайн). Весь интерфейс персонала — единое
Telegram Mini App (не отдельная веб-панель + отдельный бот, как было в
исходном плане — решение поменялось по ходу разработки). Общая
SQLite-база (WAL).

**Вход:** только по Telegram ID, без пароля (кроме самого первого раза для
нового сотрудника — см. «Онбординг нового сотрудника» ниже). Сессия не на
cookie (Telegram-вебвью ненадёжно их сохраняет между запросами), а на
подписанном токене `?t=...`, который прокидывается через каждую
ссылку/форму/редирект (`webapp/deps.link()` и `webapp/templating.render()`).

## Онбординг нового сотрудника

Входа по паролю нет вообще, поэтому нового сотрудника подключает владелец
вручную:
1. `python -m core.bootstrap <login> <password> <имя>` — создать аккаунт
   (роль передаётся внутри команды, см. файл).
2. Попросить сотрудника прислать свой Telegram ID (например, через
   `@userinfobot`).
3. `python -m core.link_telegram <login> <telegram_id>` — привязать.
4. Дальше сотрудник просто открывает бота — входит по ID, без пароля.

## Локальный запуск (разработка)

```
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env   # CRM_SECRET_KEY, CRM_BOT_TOKEN, CRM_MINIAPP_URL
export $(cat .env | xargs)
python -m core.bootstrap owner <пароль> "Имя владельца"
python -m core.link_telegram owner <telegram_id>
uvicorn webapp.main:app --reload --port 8099   # веб-часть mini app
python -m bot.bot                               # бот (меню открывает mini app)
```

## Тесты

`python simulate_tests.py` — сценарные тесты ядра (клиент→устройство→ремонт,
полный пайплайн ремонта, приход, продажи со списанием и нехваткой остатка,
telegram initData, url-токен). Работают на временной SQLite-базе во
временной директории, живую базу не трогают. Обязательны перед каждым
деплоем.

**Важно:** при ручном smoke-тесте через curl на живом сервере всегда
задавать `CRM_DB_PATH` на временный файл, либо вручную чистить тестовые
записи из `crm.sqlite3` после — один раз уже забыли и замусорили прод-базу
тестовым клиентом/товаром/ремонтом, пришлось чистить вручную.

## Деплой (Server-First, манифест п.8)

Продовая директория на BlueVPS: `/opt/electronics_crm`. Реальный процесс
пока проще, чем классический candidate/live манифеста (проект молодой,
один разработчик): rsync прямо в `/opt/electronics_crm` (с исключениями
`.venv`, `.git`, `.env`, `crm.sqlite3*`) → `simulate_tests.py` в venv на
сервере → `systemctl restart crm_web` (`crm_bot` перезапускать только если
менялся код бота) → проверка `journalctl -u crm_web -f`. Когда сотрудников
станет больше — вернуться к полноценному candidate-шагу.

systemd-юниты: `crm_web.service` (uvicorn на 127.0.0.1:8099), `crm_bot.service`
(polling). nginx + certbot на `crm.2.59.217.221.sslip.io` проксирует на
:8099 (паттерн как у `taki-verify`).

## Нельзя (манифест п.11 + специфика проекта)

- Ручной `ALTER TABLE` — только через `_ensure_column()` в `core/storage.py`.
- Хранить `CRM_SECRET_KEY` / `CRM_BOT_TOKEN` в репозитории — только в `.env`
  на сервере (в `.gitignore`).
- Списывать/перемещать товар в обход `core/inventory.record_movement()` —
  это единственный путь, который держит `stock` и `stock_movements` в
  согласованном состоянии.
- Полагаться на cookie/сессию для аутентификации в вебе — Telegram-вебвью
  их не держит между запросами, поэтому вся навигация обязана прокидывать
  `?t=` токен через `link()`/`render()`, иначе пользователя выкинет на
  повторный вход.
