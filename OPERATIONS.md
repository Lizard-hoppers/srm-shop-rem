# OPERATIONS — Electronics CRM

Сверяться с этим файлом в начале и в конце каждой рабочей сессии (правило
Clean & Live Bot Manifest, п.10).

## Что это

CRM для магазина электроники + мастерской по ремонту: клиенты, склад по
ячейкам, ремонты с привязкой к мастеру, приход комплектующих от
поставщиков, продажи (онлайн/офлайн). Весь интерфейс персонала — единое
Telegram Mini App (не отдельная веб-панель + отдельный бот, как было в
исходном плане — решение поменялось по ходу разработки). Общая
SQLite-база (WAL).

**Вход:** только по Telegram ID, без пароля (кроме самого первого раза для
нового сотрудника — см. «Онбординг нового сотрудника» ниже). Сессия не на
cookie (Telegram-вебвью ненадёжно их сохраняет между запросами), а на
подписанном токене `?t=...`, который прокидывается через каждую
ссылку/форму/редирект (`webapp/deps.link()` и `webapp/templating.render()`).

**Роли (RBAC):** `owner`/`admin`/`master`/`storekeeper` в колонке
`staff.role`, проверяются через `webapp/deps.require_role(*roles)` (поверх
`require_staff`). `/reports` — только owner+admin; мутации склада
(`/inventory/products`, `/cells`, `/movements/*`) — owner+admin+storekeeper;
мутации ремонтов (создание/статус/назначение/цена/детали) —
owner+admin+master. Просмотр списков (GET) открыт всем залогиненным. До
18.08 ролей не было вообще — любой залогиненный видел выручку и мог
списывать склад, см. commit `2c0d491`.

## Единая база, точки, журнал документов (Заход 1, 06.10)

**Одна база на весь бизнес.** Вместо отдельного SQLite-файла на магазин
(Фаза A, 23.08) — один `crm.sqlite3`; точка — это строка в `locations` и
`location_id` на всём, что в ней произошло. Причина: перемещения между
точками, общая история клиента по номеру, резерв на другой точке и «в
товаре по всему бизнесу» на трёх файлах не делаются. Перенос —
`tools/merge_stores.py` (разовый, выполнен 06.10: Магазин 1 стал базой,
«Гибрид сервис» и «Магазин» — точки 2 и 3; их файлы были пустые).
`stores.json` и `store2/3.sqlite3` больше никем не читаются (лежат в
`/root/crm_backups/retired_06_10/`).

- **`locations`** — имя/адрес/телефон/часы/канал продаж (то, что правит
  «Кабинет магазина») + id рабочих Telegram-групп и тем (раньше были в
  `stores.json`; теперь правятся прямо в таблице, UI для них нет).
  `core/stores.py` по-прежнему отдаёт `StoreConfig` («store» в коде =
  точка), `store.id` — строка, `store.location_id` — то же число.
  `core/locations.py` — мелкие выборки по точке.
- **Договорённость по `location_id` в core:** `None` при ЧТЕНИИ = весь
  бизнес, при ЗАПИСИ = первая точка. Все роуты и хендлеры бота передают
  настоящую (`webapp.deps.loc(request)`, `store.location_id`).
- **Что общее, что по точкам.** Общее: клиенты (контрагенты), каталог
  товаров, поставщики, сотрудники и мастера. По точке: ремонты, продажи,
  приходы, скупка, касса, ячейки и остатки, отчёты, счётчики на главной.
  Продажа берёт товар только из ячеек своей точки.
- **Сотрудники.** Одна строка `staff` на человека. Владелец и админ
  работают во всех точках (переключатель в «Ещё»), остальные — в своей
  (`staff.location_id`, поле «Точка» в форме мастера; пусто = первая).
  `core/store_access.py`.
- **`warehouses`** — склады: `point` (свой у каждой точки, создаётся сам),
  `master` (склад мастера — появится в Заходе 3), `transit` (единственный
  «В пути»). Ячейка принадлежит складу (`storage_cells.warehouse_id`) —
  так остаток получает точку. Код ячейки пока уникален на весь бизнес
  (старое ограничение схемы) — дубль даёт понятную ошибку; ячейка скупки
  у точек 2+ называется «СКУПКА-N».
- **Контрагент** — таблица по-прежнему `clients`, но это человек в любой
  роли. Телефон уникален (частичный индекс; без телефона — можно).
  `staff.client_id`, `staff.phone`, `suppliers.client_id` заведены под
  «один человек — клиент, мастер и поставщик» (интерфейс — Заход 6).
  Вторая карточка с тем же номером в «Клиентах» теперь отклоняется.

**Журнал документов** (`core/documents.py`, таблицы `documents` +
`document_events`). Каждая операция получает запись: тип и номер, точка,
автор, время, контрагент, сумма, статус. Экран — «Ещё → Журнал
документов» (`/journal`, владелец/админ): лента с фильтрами период /
точка / сотрудник / тип; у документа своя страница с историей.

| Тип | Префикс | Что это |
|---|---|---|
| repair | РК | ремонт клиента (номер = номер ремонта: РК-044 = «Ремонт №44») |
| sale | ПД | продажа |
| buyback | ПК | покупка (скупка) |
| receipt | ПХ | приход от поставщика |
| supplier_return | ВП | возврат поставщику |
| stock_in / writeoff / transfer | ОП / СП / ПМ | ручные складские операции |
| cash_out | РКО | расход из кассы, введённый руками |
| cash_adjust | КР | «внести/изъять» |

Префиксы — один словарь `DOC_TYPES`. Деньги от продажи/ремонта и выплата
за скупку — часть ТОГО документа, своей записи не получают. Всё, что было
до журнала, дозаполнено с исходными датами (`documents.backfill()`,
вызывается из `init_db` при каждом старте и добавляет только недостающее
— 55 документов на 06.10).

**Отмена вместо удаления** (`core/doc_cancel.py`). Проведённый документ не
удаляется: «Отменить документ» на его странице в журнале требует причину,
возвращает товар в ячейки и выводит деньги из балансов
(`cash_transactions.cancelled_at` — строка остаётся в ленте с пометкой),
документ остаётся со статусом «Отменён», кем и когда. Пока умеет: продажа,
расход из кассы, корректировка. Приход, скупка и складские документы —
вместе с партиями и счетами (Заходы 2–3).

**Защита от дубля.** Каждая форма, создающая документ, несёт скрытое поле
`idem` (токен на рендер страницы, `webapp.templating.render`); роут
строит ключ `webapp.deps.idem_key()` и, если документ с таким ключом уже
есть (`documents.find_by_key`), ведёт на него вместо создания второго. В
боте ключ — сообщение-карточка с кнопкой подтверждения (`_tap_key`).
JS-блокировка кнопки (`double-submit-guard.js`) осталась первым рубежом.

**Попутно найдено и исправлено:** продажа из нескольких позиций, упавшая
на второй из-за нехватки остатка, раньше оставляла в базе заказ и
списание первой позиции (ошибка рендерилась внутри `with get_conn()`, а
тот коммитит при обычном выходе) — теперь исключение выходит из блока и
всё откатывается. Общее правило: при ошибке посреди составной операции
выходить из `with get_conn()` исключением, а не `return`.

## Деньги: счета, смены, обмен, перемещение (Заход 2, 06.10)

**Счета** (`core/accounts.py`, таблица `money_accounts`). У точки не одна
касса, а набор независимых балансов. По умолчанию у каждой: Наличные
(UAH), Наличные USD, Наличные EUR, Счёт ФОП, Карта, Криптокошелёк USDT.
Владелец/админ правит набор в «Касса → Настроить счета»
(`/cash/accounts`): добавить, переименовать, выключить (счёт с остатком
выключить нельзя; выключенный пропадает из выбора, история остаётся).

- Баланс нигде не хранится — это сумма неотменённых строк
  `cash_transactions` счёта (`accounts.balance`). Изменить его можно
  только документом.
- `cash_transactions.account_id` — счёт; `amount` — в валюте счёта (до
  двух знаков: 12.5 USDT); `amount_uah` — гривневая оценка по курсу самой
  операции (`rate`). Отчёты и суммы документов складывают `amount_uah`.
  Строки до счетов разложены на «Наличные»/«Карта» своей точки
  (`accounts.backfill_transactions`, из `init_db`).
- `method` ('cash'/'card') — старый аргумент, всё ещё работает: выбирает
  гривневый счёт точки по умолчанию (`accounts.default_account`). Колонка
  `method` в таблице заполняется из типа счёта (на ней старый CHECK).
- `cash.cash_balance()` = только «наличные гривни» (как и раньше в
  сводках); остальные балансы — `accounts.balances()`.
- Шаблонный фильтр `| money` убирает хвост «.0».

**Оплата документа с нескольких счетов** (`cash.resolve_payments` →
`cash.record_payments`). В форме продажи и при выдаче ремонта — блок
«Оплата»: поле суммы на каждый счёт точки (`pay_<id>`), у валютного —
ещё курс (`rate_<id>`); макрос `templates/_payments.html`, разбор
`webapp/payments.py`. Части должны сойтись с суммой документа в гривне
(допуск 1 грн на валютную часть), счёт — активный и этой точки; иначе
`PaymentError` с понятным текстом и НИЧЕГО не записано. Продажа без
заполненных полей = вся сумма в наличные (один тап, как раньше). Выдача
ремонта с ценой по-прежнему требует явно указать оплату. Ремонт
оплачивается на счета точки, которая его ПРИНЯЛА. На странице документа
— разбивка «Оплата» по счетам. `sales_orders.payment_method` = тип
единственного счёта или `mixed`.

**Обмен валют** (`core/money_ops.exchange`, документ ОБ). «Отдали /
получили» — курс считается сам. Только между счетами одной точки, разной
валюты, не больше остатка. Не доход и не расход.

**Перемещение денег** (`money_ops.send_transfer` / `receive_transfer`,
документ ДП, таблица `money_transfers`). Между счетами одной валюты. На
другую точку: «Отправил → В пути → Принял» — деньги сразу уходят с
источника и ничьи, пока на точке-получателе не нажмут «Принял» (сумма по
факту; если отличается — обязательна причина, расхождение остаётся на
перемещении и в истории документа). Подтвердить может только сотрудник
точки-получателя (владелец/админ — любой). Внутри точки — мгновенно.

**Сводка за период** на «Кассе» — в гривне, «наличными / безналом»;
обмен и перемещение в неё не входят (категории `exchange`/`transfer`,
`accounts.INTERNAL_CATEGORIES`) — «деньги ≠ прибыль».

**Корректировка** («внести/изъять», документ КР) — теперь только
владелец/админ, и в вебе, и в боте: «видят все, корректируют только
владельцы». Расход, обмен, перемещение — как раньше owner/admin/
storekeeper.

**Смены** (`core/shifts.py`, таблица `shifts`, документ СМ). Смена — один
сотрудник на одной точке на один день по Киеву. Открытие: экран «сверить
остатки» (счета точки + «в товаре по всему бизнесу» по последней
закупочной цене) → «Всё совпадает» или «Есть расхождение» (текст
обязателен; смена всё равно открывается, запись уходит в журнал, а
владельцам/админам — личное сообщение от бота). Вчерашняя незакрытая
смена просто перестаёт быть текущей.
- **Бот:** действия, которые что-то записывают (Ремонт, Скупка, Приход,
  Касса), без открытой смены показывают экран сверки вместо себя
  (`_shift_gate`); после открытия действие нажимают снова. `/start`
  предлагает «💼 Открыть смену». Закрытие — кнопка в меню «Касса».
  Клиент и Сводка смены не требуют.
- **Веб:** карточка «Открыть смену» на главной, страница `/cash/shift`
  (доступна любой роли). Веб смену НЕ требует — это панель контроля.

**Отмена** дополнена: обмен и перемещение денег (в пути или уже
принятое); отмена продажи со сплит-оплатой выводит деньги со всех счетов.

**Что сознательно не вошло в Заход 2:** выбор счёта и сплит в диалогах
бота (расход в боте идёт из «Наличных»; придёт с покупкой телефона в
Заходе 4, шаги 10–11 макета); комиссия эквайринга как расход документа
(Заход 6–7, вместе с прибылью); автокурс; запрет ухода счёта в минус при
расходе/корректировке (обмен и перемещение уже не дают).

## Склад: партии, IMEI, склады мастеров, перемещения (Заход 3, 06.10)

**Партии** (таблицы `batches`, `batch_stock`; код — раздел «партии» в
`core/inventory.py`). Каждая единица остатка принадлежит партии: какой
поставщик, какой приход, сколько стоила (валюта, курс, гривневая цена
`unit_cost_uah`). `stock` остался итогом по ячейке (его читают все старые
экраны), `batch_stock` — тот же остаток по партиям; **единственный
писатель обоих — `record_movement()`**, инвариант «итог ячейки = сумма
партий» проверяется тестом `_stock_is_consistent`.

- Уход со склада берёт из конкретной партии: названной (`batch_id=`)
  либо самой старой (FIFO). Количество, размазанное по нескольким
  партиям, пишется несколькими строками `stock_movements` (по одной на
  партию) — `record_movement` возвращает id первой.
- Каждая строка движения хранит `batch_id` и снимок `unit_cost` (гривневая
  цена партии) — теперь для ЛЮБОЙ причины, не только `repair_use`.
  Себестоимость ремонта/продажи считается от реально взятой партии, а не
  от «последней закупки».
- Приход (`purchases.create_receipt`) создаёт партию на каждую строку.
  У накладной одна валюта и курс (`goods_receipts.currency/rate`; форма
  — поля «Валюта накладной» и «Курс»; для не-гривни курс обязателен).
- Возврат поставщику списывает из партии ЭТОГО поставщика
  (`purchases._return_batch`), а не просто из старейшей.
- Строка продажи хранит `batch_id` и фактическую `unit_cost`
  (`sales_order_items`) — задел под прибыль документа (Заход 6–7).
- Остаток, попавший мимо партий (старые данные, прямой INSERT),
  самолечится: `init_db` и первый же уход создают партию `source='legacy'`
  по последней известной закупочной цене.
- «В товаре» (`inventory.stock_value`) теперь точный: сумма по партиям.
- Все проверки, которые могут отказать, делаются ДО первой записи
  (`record_movement`, `create_sale`, `create_receipt`,
  `stock_transfers.send`) — несколько роутов ловят ошибку внутри своего
  `with get_conn()` и коммитят; половинчатой записи там быть не должно.

**Серийный товар** (`products.is_serial`, чекбокс «Серийный товар (учёт
по IMEI)» в карточке товара). Каждая единица — своя партия из одной
штуки с `batches.imei`.
- Приход: в строке серийного товара открывается поле IMEI (по одному в
  строке / через запятую), их должно быть ровно столько, сколько
  количество; дубль в накладной или IMEI, уже числящийся на остатке, —
  отказ всего прихода (`ReceiptError`).
- Продажа: строка серийного товара требует IMEI (`imei_N`; подсказки —
  единицы этой точки, сканер штрихкода IMEI сам добавляет строку);
  без него или с чужим IMEI — `SaleError`. Одна строка — одно устройство.
- «Добавить остаток» на карточке серийного товара — по одному, с IMEI.
- Сканер на «Складе» (`/warehouse/find`) понимает IMEI → карточка товара.
- Скупка «на продажу» создаёт серийный товар; серийник = IMEI партии,
  сумма выкупа = себестоимость.
- Один IMEI — одна единица на остатке одновременно (тот же телефон может
  вернуться позже новой партией).

**Склады** (`core/warehouses.py`, экран «Склад → Склады»
`/inventory/warehouses`). Три вида: точка, мастер, «В пути». У каждого
мастера склад появляется при создании (`auth.create_master` →
`storage.ensure_master_warehouse`; существующим создан при миграции) с
одной служебной ячейкой `МАСТЕР-<id>`; у «В пути» — ячейка `В-ПУТИ`.
Обзор показывает по каждому складу позиции, штуки и стоимость; внутри —
остаток по партиям. На карточке товара — секция «Партии на остатке»: где
каждая партия (включая другие точки, мастеров, в пути).

**Перемещение товара** (`core/stock_transfers.py`, экран «Склад →
Перемещение» `/transfers`, документ ПМ).
- Отправка сразу уводит товар в «В пути»: он не у отправителя, не
  продаётся и ещё не числится за получателем. Каждая строка — конкретная
  партия в конкретной ячейке (телефон — по IMEI).
- «Принял» говорит тот, кто отвечает за склад-получатель
  (`warehouses.may_receive`): мастер за свой, кладовщик точки за её
  склад, владелец/админ за любой. Количество по каждой строке, ячейка
  назначения (по умолчанию — где уже лежит этот товар, иначе первая).
- Принято меньше → обязателен текст; недостающее остаётся «в пути» с
  пометкой «недостача» до решения владельца — кнопка «Списать недостачу»
  (отдельный документ СП).
- Откуда кто отправляет (`warehouses.sendable_from`): мастер — со своего,
  кладовщик — со склада своей точки, владелец/админ — с любого.
- Старая форма «Перемещение между ячейками» в «Движениях» осталась —
  это перекладывание внутри одного склада, без «в пути».

**Бот: «🔁 Перемещение»** (`bot/transfer_flow.py`; состояния
`TransferFlow` объявлены в `quick_actions.py`, чтобы общие «Отмена» и
fallback их покрывали; роутер подключён ПЕРЕД quick_actions). Куда →
поиск позиции (IMEI / штрихкод / часть названия; несколько совпадений —
кнопки) → количество (серийное — сразу 1) → «Ещё позиция» / «Отправить».
Получателю (мастеру; для точки — её кладовщикам и владельцам) бот шлёт
личное сообщение с «✅ Принял всё» и «⚠ Есть расхождение — открыть»
(мини-апп). Входящие также под кнопкой «📥 Принять (N)» в начале
диалога. **Клавиатура поменялась — сотрудникам нужно один раз отправить
боту `/start`**, чтобы появилась кнопка.

**Отмена складских документов** (`core/doc_cancel.py`): приход, ручное
оприходование, списание, перекладывание между ячейками, перемещение «в
пути». Правило одно: отменить можно, пока всё, что документ принёс,
лежит там, куда он это положил; иначе отказ целиком. Отмена продажи
возвращает товар в ТУ ЖЕ партию (тот же IMEI, та же себестоимость).

**Что сознательно не вошло:** выбор конкретной партии при списании детали
на ремонт (сейчас FIFO; будет в Заходе 5 — «запчасть только со склада
мастера»); резерв (Заход 6); инвентаризация как документ; оплата прихода
и долг поставщику (Заход 6).

## Покупка телефона (Заход 4, 06.10)

«Один телефон — одна покупка» (`core/buyback.create_purchase`, документ
ПК). Заменила «Скупку» с её ветками «на запчасти / на продажу»: купленный
телефон всегда становится серийной единицей на складе купившей точки —
партия из одной штуки с IMEI, цена покупки = себестоимость, ячейка
«СКУПКА» (у точек 2+ — «СКУПКА-N»). Что с ним дальше (ремонт,
производство, витрина) — отдельные документы следующих заходов.

- **Продавец — по номеру телефона** (обязателен): существующий контрагент
  находится, новый создаётся (имя = номер, если не указали).
- **Товар = модель.** Введённая модель ищется среди серийных товаров по
  имени без учёта регистра; нет — создаётся карточка (категория «Телефоны
  Б/У», без цены продажи). Все телефоны одной модели — единицы одной
  карточки; шаг «Модель» подсказывает купленные ранее.
- **IMEI** — не короче 8 знаков, без спецсимволов, и не числящийся на
  остатке (тот же телефон можно купить снова, когда его уже нет на складе).
- **Цена в любой валюте** (`buyback_orders.currency/rate/purchase_price_uah`);
  для не-гривни обязателен курс.
- **Оплата с нескольких счетов точки** (тот же `cash.resolve_payments`,
  расход, категория `buyback`); без разбивки — вся сумма из наличных.
  Счёт, на котором денег меньше, чем с него берут, НЕ блокирует покупку —
  в боте помечается «⚠ на счёте сейчас N» (минус уйдёт в «Проблемы»
  Захода 7).
- **До шести фото** по сторонам (`PHOTO_SLOTS`, таблица `buyback_photos`):
  в боте обязательны все шесть, в веб-форме — минимум первое.
- Всё, что может отказать, проверяется до первой записи (`PurchaseError`
  / `PaymentError`).

**Бот: «🛒 Покупка»** (`bot/buyback_flow.py`; состояния `PhoneBuy` в
`quick_actions.py`; роутер подключён перед quick_actions). Шаги: номер
продавца → 6 фото → модель (кнопки с прошлыми или текст) → IMEI → поломки
(или «Без поломок») → цена («5000», «120 USD», «$99,5», «250 USDT»; для
валюты — курс) → источник оплаты (кнопки счетов с остатками) → сумма с
него («Всё оставшееся» для гривневых; для валютного — сумма и курс) →
экран распределения («Добавить оплату» / «Изменить» / «Далее») → карточка
с фото «Проверьте и купите» → «✅ Купить». В чате остаётся альбом из
шести фото с карточкой и строка с кнопкой «🏷 Карточка и этикетка».
Шесть фото альбомом приходят шестью параллельными апдейтами — шаг фото
сериализован `asyncio.Lock` на чат (иначе гонка FSM теряла бы фото).
Блокирующая часть (сжатие шести фото, запись) — в `asyncio.to_thread`.

**Мини-апп:** «Склад → Покупка техники» (`/buyback`) — та же форма;
карточка покупки (`/buyback/{id}`): фото, контрагент, IMEI, поломки, цена,
где телефон сейчас, разбивка оплаты, **этикетка** — Code128 IMEI с
моделью и номером ПК (`/buyback/{id}/barcode.png`, `?compact=1` под
30×20 мм), печать через браузер (`window.print`, как у товара). Скан
этикетки на «Складе», в продаже и в перемещении находит именно этот
телефон. Очередь сетевой печати (`print_jobs`) к покупке не подключена —
она привязана к SKU товара.

**Дубль карточки в рабочую группу:** «Кабинет магазина → Тема «Скупка»»
(`locations.buyback_topic_id`, номер темы из ссылки на неё). Если задана
и у точки есть рабочая группа — карточка каждой покупки уходит туда
альбомом (`notify.send_album`, `buyback.post_card_to_group`). Не задана
— никуда не дублируется (так на проде сейчас).

**Отмена покупки** (журнал → документ ПК): телефон уходит со склада,
деньги возвращаются на все счета, с которых платили. Только пока телефон
лежит в ячейке, куда был куплен (не продан, не отправлен мастеру).

**Что сознательно не вошло:** кнопка «Подобрать детали» с карточки и вся
цепочка производства (Заход 5); статус «Готов к продаже»; комиссии
(«Комиссии — отдельно» на макете) — с прибылью в Заходе 6–7. Старые
записи скупки (`create_buyback_intake`, purpose parts/resale) читаются
как раньше; на проде их не было.

## Сервисный центр (Заход 5, 06.10)

**Резерв** (`core/inventory.py`, таблица `stock_reservations`): «доступно
= остаток − резерв». Резерв — это не движение: остаток на полке тот же,
но `_allocate` не даёт взять зарезервированное никому, кроме документа,
под который оно держится (`record_movement(..., reserved_for=(type, id))`
— тогда резерв уменьшается на взятое). `reserve / release / reserved_qty /
available_qty`; просроченный (`expires_at`) резерв ничего не держит.
Продажа, перемещение и «Указать запчасть» смотрят на свободный остаток.

**Ремонт клиента** (`core/repairs.py`):
- Запчасть списывается с конкретной партии и ТОЛЬКО со склада исполнителя
  (`parts_warehouse`): мастер — со своего склада мастера, не-мастер — со
  склада точки. `available_parts`, `use_part(batch, cell, qty)`; чужая
  полка → `RepairPartError`. Чтобы у мастера что-то было — «🔁
  Перемещение» точка → мастер.
- «Без запчасти» — отдельное заявление (`repair_orders.no_parts`), а не
  молчание. Пока не сказано одно из двух — `needs_part` = «Нужна запчасть».
- Карточка в группе (`card()`): «РК-044 • статус / Клиент / Устройство /
  Работа / Ответственный / Запчасть / Цена», кнопки «⚙️ Указать запчасть»
  и «✅ Готово». «Готово» без запчасти ремонт НЕ закрывает: мастеру в
  личку уходит выбор (`bot/repair_actions.py`, `rp_pick / rp_none /
  rp_done`) — по кнопке на партию с его склада.
- Прибыль (`finance`): цена − себестоимость запчастей = база → доля
  мастера (его % или фикс за ремонт) → прибыль фирмы. При входе в «Выдан»
  `settle`: начисление мастеру в `master_accruals` и `profit` у документа
  РК; при выходе из «Выдан» `unsettle` снимает оба. Блок «Прибыль
  ремонта» на карточке видят только owner/admin.
- Приём в боте: «🔧 Принять ремонт»; знакомому номеру имя не
  переспрашиваем; мастер выбирается кнопкой «👤 Мастер» на карточке
  подтверждения (шагов по-прежнему 6).

**Производство / наш ремонт** (`core/production.py`, `/production`,
документ ПР): телефон фирмы уходит мастеру с нашими деталями и
возвращается с новой себестоимостью. Прибыли и расхода тут нет.
1. `draft` — заказ по IMEI (со страницы «Наши ремонты» или кнопкой «🔍
   Подобрать детали» на карточке покупки); телефон сразу в резерве.
   «Детали со всех складов» — свободные остатки запчастей всех точек и
   мастеров с поставщиком, закупкой и ценой партии; «Зарезервировать»
   заменяет подбор целиком. Мастер (фильтр Штатный/Аутсорс, навыки) +
   стоимость работы.
2. `in_work` — «Передать в производство»: по одному перемещению с каждого
   склада-источника, принятому сразу; телефон и детали на складе мастера
   и держатся под заказ (в клиентский ремонт их не списать). Мастеру в
   личку — уведомление с кнопкой «📝 Отчёт мастера» (`core/links.py`).
3. `reported` — отчёт: сколько наших деталей использовано, свои детали
   мастера (название + сумма), работа. Сдаёт мастер заказа или склад за
   него; можно пересдать до приёмки.
4. `done` — «Принять результат» (owner/admin/кладовщик): использованное
   списывается (`repair_use`, ref `production_order`), себестоимость
   партии телефона = было + наши детали + детали мастера + работа,
   мастеру начисляется работа + его детали, телефон и неиспользованные
   детали уходят перемещением «Мастер → В пути → Точка» (его надо принять
   на точке — после этого телефон продаётся по новой себестоимости).
Отменить можно только черновик (резервы снимаются, документ остаётся
отменённым).

**Мастера:** `staff.master_kind` (staff/outsource) и `staff.skills` — в
форме мастера; на карточке мастера блок «Начисления» (`master_accruals`:
ремонты клиентов + производство). Выплата и долг мастеру — Заход 6.

**Навигация:** на «Ремонтах» вкладки «Ремонты клиентов / Наши ремонты /
Производство: готовые»; в боте «🛠 Наш ремонт» открывает `/production`
(мастеру — его заказы). Клавиатура изменилась — сотрудникам нужен /start.

**Не вошло:** отмена ПР после передачи мастеру (делается руками:
перемещения обратно); выплата начисленного; автоснятие резерва по
времени (24 ч — для заказов клиентов, Заход 6).

## Продажи, заказы, взаиморасчёты (Заход 6, 06.10)

**Взаиморасчёты** (`core/settlements.py`, таблица `client_ledger`): одна
подписанная строка на всё, что меняет «кто кому должен». `amount > 0` —
клиент должен нам больше, `< 0` — меньше / мы должны ему. Баланс = сумма
живых строк: `> 0` «нам должны», `< 0` «мы должны» (аванс). Строки
отменяются вместе с документом, не удаляются.
- Продажа с клиентом пишет две строки (начислено, оплачено) — даже
  оплаченная сразу, чтобы сверка читалась как полная выписка. Покупка у
  клиента — тоже две (должны ему, заплатили).
- «Принять деньги» = ПКО (`cash_in`), «Выдать деньги» = РКО (`cash_out` с
  `ref_table='client_ledger'`); деньги — на любые счета точки, валютный
  счёт с курсом. Выдать может только owner/admin, принять — любой.
- `statement()` — «Сверка за период»: входящий баланс, строки с
  нарастающим итогом, обороты, исходящий баланс. `debtors()` — все с
  ненулевым балансом (пойдёт на Главную в Заходе 7).
- Ремонты клиентов в ledger НЕ пишутся (оплата при выдаче, долга нет) —
  в карточке клиента они видны в «Документах».

**Продажа «в долг»** (`sales.create_sale(..., allow_debt=True)`): можно
внести меньше суммы, остаток — на баланс клиента; только с клиентом
(телефон). Пустая «Оплата» + галочка = вся сумма в долг
(`payment_method='debt'`). Больше суммы — по-прежнему ошибка. У документа
ПД теперь есть `profit` (сумма − себестоимость строк, если она известна).

**Заказ клиента** (`core/orders.py`, `/orders`, документ ЗК): создаётся из
формы продажи кнопкой «Отложить на 24 часа» (нужен телефон клиента).
- `reserved` — строки в резерве до `reserved_until` (24 ч); продать,
  переместить или списать их нельзя.
- «Оплатить» — любая часть остатка, идёт авансом клиента под заказ.
- «Выдать» — заказ становится продажей ПД ровно тех партий, что держал;
  в форме выдачи вписывается, что клиент платит сейчас; не оплаченное —
  его долг.
- «Автоснятие»: резерв перестаёт держать товар в момент истечения
  (`expires_at`), а `expire_due()` (вызывается при любом показе/действии с
  заказами) переводит заказ в `expired`. «Возобновить/Продлить резерв» —
  ещё 24 ч, если товар всё ещё свободен.
- Отмена (кнопкой или из журнала) снимает резерв; оплаченное остаётся
  авансом клиента — возвращается через «Выдать деньги». Отмена продажи,
  вышедшей из заказа, закрывает и заказ.

**Карточка клиента** (`/clients/{id}`): «нам должны / мы должны»,
прибыль по документам (owner/admin), кнопки «Купить» (`/buyback?phone=`),
«Продать» (`/sales?phone=&name=`), «Принять деньги», «Выдать деньги»,
«Сверка за период» (`/clients/{id}/statement`), все документы клиента с
суммой и прибылью, открытые заказы.

**Мастер** (`/masters/{id}`): начислено / выплачено / мы должны,
«Выплатить мастеру» — РКО (`cash_out` с `ref_table='master_payouts'`),
список выплат. Выплата больше начисленного допускается (аванс) — «мы
должны» уходит в минус. Отмена РКО из журнала возвращает и деньги, и
долг.

**Бот:** «🛍 Продажа» (`bot/sale_flow.py`, состояния `SaleFlow`): IMEI
или часть названия → цена (кнопка с ценой из карточки) → телефон клиента
(обязателен; имя — только у нового номера) → гривневый счёт одним тапом
или «В долг» → подтверждение → карточка в чат и в рабочую группу (тема
«Продажи», если задана). Один товар за раз; несколько товаров, сплит по
счетам, валюта — кнопка-ссылка на форму в приложении. «👤 Клиент» в боте
показывает баланс и ведёт на карточку и сверку. Клавиатура изменилась —
сотрудникам нужен /start.

**Отмена из журнала** добавилась для ПКО, РКО контрагенту, выплаты
мастеру и заказа клиента (`core/doc_cancel.py`).

**Не вошло:** долг по конкретной продаже отдельно не ведётся (только
общий баланс клиента); старые продажи/покупки в ledger не перенесены

## БАГ+ФИКС: кнопки «🛠 Наш ремонт» и «🛍 Продажа» молчали в боте (06.10)

Павел: «кнопка ремонт не работает, бот виснет». В логах — `Update … is
not handled`, ошибок нет. Причины две, обе про точное совпадение текста
кнопки reply-клавиатуры с `F.text == BTN_…`:
1. Клиент Telegram при нажатии дописывает к некоторым эмодзи невидимый
   селектор U+FE0F («🛠 Наш ремонт» приходит как «🛠\ufe0f Наш ремонт»).
   Затронуты эмодзи с текстовым представлением по умолчанию — из наших
   это 🛠 и 🛍, обе кнопки добавлены в Заходах 5–6.
2. Кнопка «🔧 Ремонт» переименована в «🔧 Принять ремонт», а старая
   клавиатура остаётся у человека на экране, пока бот не пришлёт новую.

Фикс: `ButtonTextMiddleware` (`bot/quick_actions.py`) приводит входящий
текст к каноничной подписи кнопки до фильтров; старая «🔧 Ремонт» снова
запускает приём и присылает новую клавиатуру; `bot/fallback.py` (последний
роутер) на любой неузнанный текст сотрудника отвечает актуальной
клавиатурой и пишет этот текст в лог.

**Почему не поймали тесты:** сценарии бота вызывали функции-обработчики
напрямую, минуя фильтры и порядок роутеров. Теперь есть
`scenario_bot_dispatch`: каждая кнопка клавиатуры (как написана и с
U+FE0F) подаётся настоящему диспетчеру из `bot.bot.build_dispatcher()`.
**Правило:** новая кнопка reply-клавиатуры считается проверенной только
после этого сценария; эмодзи в подписи — любое, middleware справится.

**Кнопки на карточке (18.08).** Карточка не статичная — под ней кнопки,
которые ведут ремонт по статус-пайплайну прямо из Telegram, без захода в
приложение:
- `new` → «🔧 Взять в работу» (`repair_take:{id}`) — атомарно
  (`core/repairs.claim_repair()`, `UPDATE ... WHERE status='new'` +
  проверка `rowcount`, а не слепой `UPDATE` — вторая одновременная попытка
  просто проигрывает гонку, а не тихо перезаписывает первую). Если на
  приёме уже назначили конкретного мастера — кнопка реально сработает
  только для него (или admin/owner), остальные получат алерт «Закреплено
  за …».
- `in_progress` → «✅ Готово» (`repair_done`, только для взявшего мастера
  или admin/owner с `override=True`) и «↩️ Отменить» (`repair_release`,
  возврат в `new` без мастера — на случай, если взяли по ошибке).
- `ready`/`issued`/`cancelled` → кнопок нет.

Карточка **редактируется на месте** (`core/notify.edit_message()` /
`sync_repair_cards()`), а не дублируется новым сообщением — какое именно
сообщение редактировать, знает новая таблица `repair_order_messages`
(`chat_id`+`message_id` на каждый отправленный адресат). Синхронизация
двусторонняя: ручная смена статуса из приложения (`POST
/repairs/{id}/status`) тоже дёргает `sync_repair_cards()` — кнопка в
Telegram и статус в приложении никогда не расходятся, старая карточка не
может позволить нажать «Готово» на том, что уже закрыли из приложения.

Обработчики кнопок — `bot/repair_actions.py` (три `callback_query`
хендлера, зарегистрированы в `bot/bot.py`), сотрудник определяется по
`callback.from_user.id` через `core.auth.get_staff_by_telegram_id()` —
тот же путь, что и вход в веб-панель.

**Как узнать chat_id/thread_id новой темы:** добавить бота в группу как
админа → открыть тему → скопировать номер из ссылки `t.me/c/<internal_id>/<thread_id>`
(chat_id = `-100<internal_id>`), либо отправить `/chatid` в общем чате
группы (не в теме) — бот ответит числом chat_id самой группы. thread_id
темы командой не достать, только из ссылки на сообщение в этой теме.

на подгруппу под каждого выбранного мастера — обсудить структуру, когда

проде, не свежий `CREATE TABLE`). 146/146 тестов. Проверено вживую:

фото реально легло на диск + отдалось по `/static/product_photos/...`.

**Баг и фикс 18.08 (commit `7d7fdba`): загрузка фото товара «вешала»
мини-приложение.** Причина — в `/etc/nginx/sites-available/crm-miniapp`
не было `client_max_body_size`, действовал дефолт nginx 1 МБ; реальное
фото с камеры — обычно 2-8 МБ. Форма загрузки была обычным `<form
enctype="multipart/form-data">` (нативная навигация браузера, не AJAX) —
когда nginx резал запрос, странице некуда было вывести ошибку, и
Telegram WebView просто зависал на пустом экране в процессе навигации
(сам Telegram не падал). **Важно помнить:** у этого домена nginx
настроен без `client_max_body_size` по умолчанию — если добавляется

## Печать по сети (Ethernet) — очередь + локальный агент (19.08, commit `9f09cf5`)

Павел подключил Xprinter XP-420B по Ethernet и захотел печатать прямо с
сервера CRM по сети. Уточнил: сервер CRM (облако) физически не может

**Архитектура:** кнопка «📡 Отправить на печать» на карточке товара

принтером-этикетником, агенту не нужно знать «сырой» язык команд
принтера). Старый способ печати напрямую через браузер (USB,

## Мультимагазинность (Фаза A+B+C+D, 23.08) — АРХИТЕКТУРА ЗАМЕНЕНА 06.10

> **С 06.10 всё ниже про «отдельный файл на магазин», `stores.json`,
> identity-строку владельца в каждой базе и `--store=` — история.**
> Действует раздел «Единая база, точки, журнал документов» выше.
> Переключатель, «Кабинет магазина», «Все магазины» и резолвинг магазина
> по chat_id группы работают как раньше, только поверх одной базы.

**Архитектура:** отдельный файл SQLite на каждый магазин (не колонка
`store_id` в общей БД — вариант обсуждался и отклонён как требующий
протаскивать фильтр по магазину буквально в каждый запрос по всему проекту).
Один веб-процесс и один бот-процесс обслуживают все магазины разом; какой
файл БД открыть на конкретный запрос решает `core/storage.py` через
`contextvars.ContextVar` (`set_current_db_path`/`get_conn()` без явного
пути читает контекст), которую выставляет middleware в `webapp/main.py` на
каждый HTTP-запрос по `store_id` из подписанного `?t=` токена
(`core/session_token.py`).

**Реестр магазинов — `stores.json`** в корне репо (по аналогии с `.env`:
деплоится вручную на сервер, **не коммитится**, шаблон — `stores.json.example`
в git). Формат: список `{id, name, db_path, staff_group_chat_id,
repair_topic_id, masters_group_chat_id}`. Если `stores.json` на сервере нет
(старое окружение) — `core/stores.py` синтезирует один магазин из
существующих `CRM_DB_PATH`/`CRM_STAFF_GROUP_CHAT_ID`/... в `.env` — полная
обратная совместимость для однобазового деплоя без единой правки конфига.

**`store_settings`** — таблица внутри БД **каждого** магазина (name/address/
phone/working_hours, singleton-строка id=1) — редактируется через «Кабинет
магазина» (`/store/settings`, owner/admin, карточка в «Ещё»,
`core/store_settings.py` + `webapp/routers/store.py`). Название магазина из
этой таблицы (не из `stores.json`, тот остаётся чисто инфраструктурным)
показывается мелкой подписью под заголовком экрана в шапке — только если
магазинов больше одного (`webapp/templating.py::render()`).

**Выбор магазина при логине и переключатель (Фаза B, 23.08).**
`/miniapp/auto` теперь реально сканирует identity этого `telegram_id` по
ВСЕМ настроенным магазинам (`core/store_access.py::accessible_stores()`,
общий хелпер для логина и переключателя) — единственное совпадение
логинит сразу туда, несколько (только у owner/admin — своя identity-строка
в каждой БД) разрешаются через «последний использованный магазин»
(`core/store_prefs.py`, отдельный крошечный `store_prefs.sqlite3`, т.к.
у identity нет единого места хранения — она размазана по базам магазинов),
с фолбэком на первый магазин по конфигу, если предпочтения ещё нет.
Переключатель — `/store/switch` (карточка «Сменить магазин» в «Ещё», видна
только если у сотрудника реально больше одного доступного магазина);
переключение всегда идёт через тот же `accessible_stores()` — нельзя
переключиться туда, где для этого `telegram_id` нет identity-записи, и
выданная роль всегда берётся из БД **целевого** магазина, не текущего.

**Бот таргетит по магазинам (Фаза C, 23.08).** `core/notify.py::notify_repair_card()`/
`notify_staff_group()` берут группы именованными параметрами (дефолт —
легаси `CRM_*_GROUP_CHAT_ID` из `.env`, для обратной совместимости);
`webapp/routers/repairs.py` передаёт группы ТЕКУЩЕГО магазина запроса.
Один бот-процесс/один токен обслуживает чаты всех магазинов —
`core/stores.py::store_for_chat_id(chat_id)` резолвит, какой группе какой
магазин принадлежит, `bot/repair_actions.py` (кнопки на карточке) и
`bot/repair_attachments.py` (фото-реплай) резолвят магазин по chat_id
ПЕРЕД тем как открыть БД (order_id в callback_data не уникален глобально
между магазинами). Личка (`bot/purchase_photo.py`, приход накладной по
фото) резолвится по идентичности отправителя — `core.store_access`
(тот же механизм, что переключатель), store_id едет прямо в
callback_data черновика, чтобы не переоткрывать резолвинг не в тот
магазин между отправкой фото и нажатием «Оприходовать».

**Сводный отчёт «Все магазины» (Фаза D, 23.08).** `GET /reports/all-stores`
(owner/admin, карточка в «Ещё» рядом с «Сменить магазин», гейт
`multi_store_access`) — по карточке на каждый магазин, к которому у
текущего сотрудника реально есть доступ (`core.store_access.accessible_stores()`,
не слепо по всем `stores.json`), плюс строка «Итого». All-time, без
периода — ни `core/reports.py`, ни `core.cash.cash_balance()` период не
поддерживают, а изобретать его отдельно для одной сводки не стали.
6 метрик на магазин (в работе / продаж штук / дефицит склада, выручка
ремонтов / выручка продаж / касса) — переиспользуют уже готовые функции
`core.reports`/`core.cash`/`core.inventory`, композиция прямо в роутере
(`webapp/routers/reports.py`), без новой core-абстракции. Без разбивки по
мастерам — у `core/masters.py` нет функции "сводка по всем мастерам
сразу", и сопоставлять identity мастеров между магазинами не на чем
(каждый мастер существует только в своей БД).

Мультимагазинность полностью реализована (Фазы A-D). Возможные будущие
доработки — не запланированы, по запросу: разбивка по мастерам в сводке,
период в отчётах, отдельные боты на магазин.

**Самостоятельная регистрация клиента через личку бота** (человек сам
пишет боту, до контакта с персоналом) сознательно оставлена как есть —
всегда попадает в дефолтный магазин, независимо от того, сколько

## Витрина в Telegram-канале (02.10)

Бот сам выставляет карточку товара в канал продаж магазина и сам убирает
её, когда товар продан (`core/channel_posts.py`).

- **Настройка:** «Ещё → Кабинет магазина → Канал продаж» (`@username` или
  числовой id, хранится в `store_settings.sales_channel`, свой у каждого
  магазина). Бота добавить в канал администратором с правом публиковать,
  редактировать и удалять сообщения.
- **Публикация:** карточка товара → блок «Канал продаж» → описание для
  покупателя (`products.description`) → «Выставить в канал». Нужны цена и
  остаток > 0. Уходит одно сообщение: фото товара (если есть) + подпись +
  url-кнопка «Купить». Запись — в `channel_posts`.
- **Авто-снятие:** `channel_posts.sync_products()` вызывается после
  продажи, списания, расхода на ремонт, возврата поставщику и правки
  товара. Остаток 0 → `deleteMessage`; если Telegram отказал (бот может
  удалять свои сообщения только ~48 ч) → карточка правится в заглушку
  «ПРОДАНО» без кнопки. Остаток есть, но изменились имя/цена/описание →
  карточка правится на месте.
- **Кнопка «Купить»:** deep link `t.me/<бот>?start=buy_<product>_<store>` →
  `bot/channel_orders.py`: покупателю подтверждение + контакты магазина,
  сотрудникам — заявка в рабочую группу магазина: в тему `sales_topic_id`
  из `stores.json` (у Магазина 1 — тема 121), без неё — в General; а если
  группа не задана — в личку владельцу/админам. Повторный тап того же человека
  по тому же товару сотрудников не дёргает (`channel_leads`). Товар при
  этом НЕ бронируется — сделку закрывает человек через обычные Продажи.
- Ошибки Telegram продажу не ломают (тот же принцип, что `core/notify.py`).
- Не сделано (следующие шаги): статус «Забронировано», альбом из

## Деплой (Server-First, манифест п.8)

Продовая директория на BlueVPS: `/opt/electronics_crm`. Реальный процесс
пока проще, чем классический candidate/live манифеста (проект молодой,
один разработчик): rsync прямо в `/opt/electronics_crm` (с исключениями
`.venv`, `.git`, `.env`, `*.sqlite3*`) →
`simulate_tests.py` в venv на сервере → `systemctl restart crm_web`
(`crm_bot` перезапускать только если менялся код бота) → проверка
`journalctl -u crm_web -f`. Когда сотрудников станет больше — вернуться к
полноценному candidate-шагу.

systemd-юниты: `crm_web.service` (uvicorn на 127.0.0.1:8099), `crm_bot.service`
(polling). nginx + certbot на `crm.2.59.217.221.sslip.io` проксирует на
:8099 (паттерн как у `taki-verify`).

## Нельзя (манифест п.11 + специфика проекта)

- Ручной `ALTER TABLE` — только через `_ensure_column()` в `core/storage.py`.
- Удалять проведённый документ или строку кассы/движения — только отмена
  через `core.doc_cancel` (причина, автор, запись остаётся в журнале).
- Создавать операцию в обход её core-функции (`create_sale`,
  `create_repair`, `record_expense`…) — именно они пишут запись в журнал
  документов; прямой `INSERT` оставит операцию без документа до
  следующего старта (`documents.backfill`).
- Читать/писать «по точке» без `location_id` из роута или хендлера —
  `None` означает «весь бизнес» при чтении и «первая точка» при записи.
- Хранить `CRM_SECRET_KEY` / `CRM_BOT_TOKEN` / `PRINT_AGENT_TOKEN` в
  репозитории — только в `.env` на сервере (в `.gitignore`).
  `tools/print_agent.py` коммитится без значения токена (читает его из
  переменной окружения на машине Павла).
- Прогонять `simulate_tests.py` с полным `source .env` — экспортировать
  только ту одну переменную, которая реально нужна для проверяемой
  фичи (см. инцидент 19.08 выше про печать).
- Списывать/перемещать товар в обход `core/inventory.record_movement()` —
  это единственный путь, который держит `stock` и `stock_movements` в
  согласованном состоянии.
- Полагаться на cookie/сессию для аутентификации в вебе — Telegram-вебвью
  их не держит между запросами, поэтому вся навигация обязана прокидывать
  `?t=` токен через `link()`/`render()`, иначе пользователя выкинет на
  повторный вход.
